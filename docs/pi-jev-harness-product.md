- harness 的范围为：工具路由与计划校验、动作评审、证据收集、完成验收、有界续跑、上下文裁剪和运行记录。

## 1. 最终交付的是什么

**pi-jev-harness 是一个本地运行、可安装到 Pi 的开发任务增强包。开发者继续用自然语言交代开发任务，产品帮助选择工具、跟进执行与验证，并交付可核对的结果。模型由用户或 magpie 决定。**

它的日常使用形态有两个：在 Pi 中直接使用的扩展，以及执行同一套流程的 `pi-jev` 命令行。两者共享任务控制逻辑，不形成两套独立的执行系统。

用户交给产品的内容可以是：

> 修复空列表时分页按钮仍可点击的问题，补回归测试，不改变现有接口。

产品应在已有授权范围内完成检查、修改和验证。需要补证据时继续执行；确实缺少凭据、权限或用户决策时，明确说明阻塞。最后交付代码改动、检查结果、完成情况及运行报告，而不只是给出一份工具选择建议。

Jev 在其中负责工具候选选择和窄范围判断，代码生成、工具执行和会话管理继续由 Pi 及用户选定的开发模型承担。用户无需理解概率分布、问题集版本或内部评审记录才能正常使用。

**产品价值主张：在任务质量不退化的前提下，减少等待、无效工具调用和返工，让开发任务更快走到有证据的完成状态。** 这是待验证的目标，不是已有测量结论。

## 2. 用户拿到的具体产物

交付需要区分“安装的软件”和“软件完成任务后产生的结果”。

| 层次 | 实际交付物 | 用户如何使用 |
| --- | --- | --- |
| 项目源码 | `<repo>` 下的一套 TypeScript 项目，包含业务代码、宿主适配、测试和文档 | 开发、审查、构建和维护产品 |
| Pi 扩展 | 一个统一的扩展入口，提供任务路由、过程控制、状态查看及按需评估 | 安装后继续在 Pi 中输入任务，不需要换一个聊天界面 |
| 命令行 | `pi-jev`，提供 `run`、`doctor`、`report`、`replay` | 从终端启动任务、检查安装状态、查看报告和离线核对记录 |
| 可复用接口 | 可分别导入的 `router` 与 `harness` 子入口 | 其他开发工具复用工具选择和任务控制能力；不是普通用户的必经入口 |
| 使用与验证资料 | 本产品与使用说明、技术方案（含配置、故障处理和验证要求）、第三方来源台账、回归用例和对照实验记录 | 知道如何启用、关闭，以及哪些能力已经过验证 |
| 每次任务的结果 | 工作区实际改动、验证证据、完成摘要、运行记录，以及可选的完整工具输出存档 | 审查代码、判断能否接收结果、定位失败或恢复被移出的信息 |

首版以本地扩展和命令行为主，不要求部署 Web 服务、使用一个新的账号系统或打开额外管理后台。安装过程与启用外部 Jev 请求分开。

## 3. 面向谁，解决哪些问题

主要用户是已经使用 Pi 开发代码、希望减少等待和返工的开发者。命令行脚本调用者是第二类用户；把 router/harness 嵌入其他工具的维护者是扩展用户。

产品围绕一条开发任务从开始到完成的过程工作：

| 用户遇到的问题 | 产品提供的行为 | 用户能够观察到的变化 |
| --- | --- | --- |
| 工具很多，但当前任务只需要一小部分 | 暴露相关工具及其必要前置能力，并在任务内尽量保持稳定 | 少走无关工具调用；需要读文件时不会只剩编辑工具 |
| 修改方向偏了，做完才发现 | 在有价值的动作或阶段边界检查任务范围与证据 | 尽早指出具体偏差，而不是持续追加无关改动 |
| 模型说“完成”，实际上缺检查或还有失败 | 对照验收要求查看实际改动与检查结果 | 完成声明带证据；缺口和不可验证项清晰可见 |
| 已经能继续，却总等用户说“继续” | 在既有授权内执行有次数和预算上限的续跑 | 不需要为同一明确目标反复确认；遇到真实阻塞则停下 |
| 长日志挤占上下文，之后又要重复运行工具 | 对符合条件的输出做可恢复裁剪，保留完整存档 | 需要时读取原输出，而不是重新执行可能有副作用的操作 |

模型和思考档位的选择不在本产品范围，由用户或 magpie 决定，见第 7.1 节。

简单问答和很短的任务允许走原生快速路径。产品不要求每次读取、每条命令或每轮对话都增加一次 Jev 判断。

## 4. 产品形态与使用入口

### 4.1 在 Pi 中使用

这是默认入口。开发者保持原有习惯：打开项目，提出任务，查看进度，审查结果。

扩展提供少量控制命令：

| 拟定命令 | 产品行为 |
| --- | --- |
| `/jev status` | 查看当前模式、实际启用的能力、本次任务状态及剩余续跑预算 |
| `/jev mode off` | 关闭 Jev 增强行为；之后不再派发新的 Jev 请求，取消或丢弃在途决策，后续按原生流程运行 |
| `/jev mode shadow` | 记录 Jev 建议，但不据此改变工具集合、续跑或上下文 |
| `/jev mode on` | 启用已配置、已通过对应验证的能力；未满足条件的能力仍保持关闭或观察状态 |

`on` 不是“所有实验能力全部打开”。状态显示必须逐项对应真实行为，不能仅因为配置文件写着 on 就显示已启用。

兼容已有的 `jev_route`、`jev_acceptance_gate`、`foreman_assess` 工具名，供模型或高级用户按需调用；`jev_route` 只给出工具与计划建议，不再给出模型建议。产品自动流程调用同一套能力，避免一个阶段重复评估和重复收费。启用输出裁剪时，提供受控的 `jev_recall` 读取入口。

### 4.2 从终端使用

拟定命令接口示例：

```text
pi-jev doctor
pi-jev run --cwd <项目目录> "修复空列表分页按钮，并补回归测试"
pi-jev report <运行编号>
pi-jev replay <记录文件>
```

`run` 在明确的工作区启动 Pi 会话，展示进度，并等待任务完成、失败、取消或阻塞后返回。它与扩展入口使用相同规则和结果定义。

`doctor` 默认只检查本地安装、配置、重复加载和凭据是否存在，不测试付费服务，也不打印密钥。`replay` 是离线核对历史记录与所绑定的策略和输入，不重跑历史命令、不再次应用补丁；策略或输入不匹配时应报告无法复核，而不是伪造一致。

供脚本调用时，输出应包含运行编号、任务状态、工作区、变更列表、验证结果、报告位置，以及阻塞或失败原因。进程正常结束与任务成功完成必须区分，不能让“允许退出”被脚本误判为“任务成功”。

### 4.3 首次使用顺序与运行状态

首版代码已实现，但尚未打包发布，不提供发布版安装命令；开发期加载方式与现有命令见第 15 节。按以下顺序使用：

1. 在目标仓库运行 `pi-jev doctor`，检查本地加载和配置状态；指定其他工作区时使用 `run --cwd <项目目录>`。
2. 确认 `/jev status` 显示的实际模式与能力。默认 `off`，先保留原生 Pi 流程。
3. 明确决策服务、可发送的数据和请求预算后，再选择 `shadow` 观察；只对已配置且通过验证的能力选择 `on`。三种模式的含义见第 10 节。
4. 输入任务、查看必要的阶段进度，结束后审查工作树与结果摘要；需要更多依据时使用 `report`，离线核对决定时使用 `replay`。

以下是运行中状态的示意，不是当前运行结果：

```text
Jev：shadow
当前任务：修复分页异常
阶段：验证
模型：用户选定（harness 不改写）
增强状态：工具路由仅观察；自动续跑关闭；上下文裁剪关闭
当前结果：待相关检查完成
```

主界面只显示必要阶段与重要变化，完整评分放在运行详情中。用户可以追问、补充约束或取消；新要求与在途旧决定的处理遵循第 5 节，取消与保留成果的状态遵循第 8 节。

## 5. 一次任务如何完成

### 第一步：明确任务和工作区

开发者提供目标、已有约束和必要的验收条件。产品使用当前会话或命令明确指定的项目，不猜测另一个仓库。

已经清楚的任务直接开始。只有缺失信息会实质改变结果、范围或授权时才提问。例如，“把这个模块改好”需要明确希望改善什么；“修复空列表分页并补测试”不应被追问是否允许开始检查代码。

### 第二步：准备执行方式

产品根据可用工具、用户指定和已启用策略，选择工具配置。一个可用候选可以直接使用，无需让 Jev 再选择一次。模型由用户在 Pi 中选定；选的是 magpie 的模型或路由组时，由 magpie 决定每次请求由哪个成员模型或账号服务。产品不选择、不切换模型。

普通开发者看到的是必要的简短说明，例如“沿用你选定的模型，已准备读取、编辑和测试能力”。评分和完整决策记录放到展开信息或运行报告中。

### 第三步：执行并记录实际结果

Pi 负责读取、编辑、新建文件和执行已授权检查。产品关联本次任务的实际改动与结果，保留任务开始前的用户改动，不把原有测试失败算成本次引入，也不把其他人的改动当成本次成果。

修复任务按项目约定先取得失败证据，再修改并验证；对于明确的新功能，用户要求本身就是实施依据，不需要捏造一个已有缺陷。检查失败、方向变化或等待用户处理时及时说明。常规成功操作不必逐条刷屏。

### 第四步：在关键节点检查缺口

短任务做轻量验收；复杂任务在里程碑查看是否偏题、是否需要独立验证、是否存在未满足的要求。不把两套评估工具在每一步重复调用。

需要的是可观察证据。例如，修复任务应有相应的复现和回归结果；解释代码的问答任务可以由准确且有依据的回答满足，不强制运行无关测试。

### 第五步：完成，或有界继续

仍有明确、可执行且无需新增用户输入的动作时，在预算内继续。首个续跑策略最多自动追加两轮；这两轮仍属于同一个用户任务。

出现新用户指令、取消、待处理审批、运行中的任务或实际外部阻塞时，不根据旧判断继续。次数或预算耗尽后报告剩余动作，不重新创建任务来绕过上限。

### 第六步：交付结果

向开发者展示“做了什么、如何验证、还有什么没完成”。运行报告提供进一步核查所需的依据。

**任务结束的标准是对用户要求给出可核对的状态，而不是主模型刚好输出了最后一句话。**

## 6. 典型场景与预期体验

下表描述目标行为，不是已经执行过的案例。

| 场景 | 输入示例 | 应有体验与输出 |
| --- | --- | --- |
| 小范围修复 | “空列表不能翻页，修复并补测试” | 定位相关逻辑，复现问题，完成修改和回归；交付改动及对应测试结果，不启动多智能体编排 |
| 跨文件新增功能 | “增加 CSV 导出，保留现有 JSON 行为” | 按要求检查涉及的文件、完成必要修改和新文件、验证两种行为；首版可以由单执行者串行完成，不把多文件等同于必须并行 |
| 长日志定位问题 | “分析构建失败并修复” | 保留当前错误和相关证据；只有裁剪能力已经过验证且启用时，才移出无关旧输出，之后可读回完整内容 |
| 外部条件不足 | “修复接口并验证线上账号流程”，但缺测试账号 | 完成不依赖账号的部分，保留本地验证；明确账号验证被阻塞，不报告整个任务通过，也不持续重试登录 |
| 纯解释任务 | “解释这个缓存为什么会失效” | 使用必要源码证据回答；不创建无关代码改动，不为了展示 harness 而增加无意义的验收步骤 |

用户途中补充“不要改公开接口”时，该约束立即成为后续工作的依据。旧范围下的在途路由或评审结果不得覆盖新指令。

## 7. 产品能力如何组合

### 7.1 模型与工具选择

用户购买或安装的价值不是“多一个路由库”，而是当前任务能以合适的工具开始，并在运行中保持可用。

模型路由由 magpie（https://github.com/yetone/magpie）负责，不在本产品内实现。用户在 Pi 中选定模型；选 magpie 路由组时，由组内的路由策略（smart、order、rotate、usage）和会话粘滞设置决定每次请求由哪个成员模型或账号服务。产品不改写用户选择，也不因评审、续跑或上下文裁剪切换模型。magpie 的安装、provider 和路由组配置在产品之外完成，产品不读取、不改写 magpie 配置。

工具选择保留必要的读取、搜索和恢复能力。任务进行中尽量保持工具菜单稳定；外部扩展或用户改变工具状态后，产品不能用旧快照覆盖这些变化。

### 7.2 行动检查与完成验收

动作发生前的检查关注目标、范围和必要的证据；任务结束时的验收关注整个要求是否得到满足。两者解决不同问题。

Jev 给出有利评审并不产生执行权限，也不证明程序正确。实际执行仍受既有授权控制，完成判定仍需要实际结果。产品不会因为某条评分较高就绕过失败测试。

### 7.3 有界续跑

续跑减少的是用户反复输入“继续”的负担，适用于已经知道下一步做什么的情况。

它不能解决缺凭据、缺权限或缺产品决策，也不应变成无限重试。界面显示已经使用和剩余的续跑次数；新一轮应能说明要补哪一项缺口。

### 7.4 可恢复上下文裁剪

这是条件启用的优化能力。产品保留用户指令、相关错误、工具调用记录，以及图片等无法可靠裁剪的内容。完整输出成功存档并可读取后，才替换当前请求中符合条件的文本。

磁盘写入失败、达到存储上限或无法保全内容时，保持原文。恢复的内容在本次使用中应保持可见，避免刚读回就再次被同一策略裁掉。

请求级裁剪与持久会话摘要替换是两个独立开关；关闭前者不能被描述为已经关闭后者。首版优先验证请求级能力，摘要替换继续由原生路径处理，直到单独通过保全验证。

### 7.5 可查看的任务记录

开发者能够从运行编号查看这次任务使用了什么配置、发生哪些改动、执行过哪些检查、哪里发生回退。默认展示结果摘要，详细数据按需展开。

报告中的缺失用量和费用显示为未知。字符数减少、token 减少、缓存命中和实际费用分开呈现，不能把其中一项直接包装成“提升了多少倍”。

## 8. 任务状态与异常体验

用户需要知道下一步该做什么，而不必解释内部错误码。

| 用户可见状态 | 含义 | 应给出的信息 |
| --- | --- | --- |
| 执行中／验证中 | 任务仍在推进 | 当前阶段和必要的进度变化 |
| 已完成 | 本次要求均有匹配的完成依据 | 变更、验证结果和报告入口 |
| 已结束，仍未完成 | 仍有缺口，或预算／续跑次数已用完 | 已完成部分、剩余项和停止原因 |
| 已阻塞 | 下一步需要当前无法取得的条件 | 具体缺什么，以及不依赖该条件的部分完成到哪里 |
| 已取消 | 用户取消或会话主动终止 | 已产生的改动与可用记录，不伪装成已回滚 |
| 执行失败 | 执行器、命令或其他环节出现无法完成的错误 | 失败环节、保留状态和相关证据 |
| 已结束，完成验收不可用 | 无法取得完整验收判断，但可以正常退出 | 已有检查结果与尚未确认的完成项，不能标记验收通过 |

组件异常与任务状态分开。例如，工具路由不可用但原生路径仍可完成任务时，显示“本次路由已回退”；不能将它伪造为 Jev 选择成功，也不必把整个任务标为失败。

若用户已经为某类动作启用强制评审，评审不可用时应阻止该动作，并说明原因。产品不能悄悄切成无评审模式继续写入。

## 9. 任务结束后看到什么

### 9.1 人能直接读的完成摘要

以下仅为输出格式示例，文件名、状态和检查描述均为示意，不是当前项目的运行结果：

```text
任务：修复空列表分页，并补回归测试
状态：已完成

改动
- 空列表不再允许进入下一页。
- 保持公开接口和正常分页行为。

验证
- 修改前已复现空列表问题。
- 修改后对应回归检查通过。
- 正常列表的分页检查通过。

运行信息
- 模型：沿用用户指定。
- 自动续跑：未使用。
- 总费用：未知，供应商未提供完整用量。

更多依据：查看本次运行报告。
```

真实输出必须来自本次运行证据。没有执行过的测试、不知道的耗时或费用不得用示例值填充。未完成任务采用同样结构，明确列出剩余项。

### 9.2 本地可核查产物

拟定默认运行目录位于工作区源码之外，可通过配置调整：

```text
~/.pi/agent/pi-jev-harness/runs/<run-id>/
  summary.md        # 人类可读的任务结果
  run.json          # 脚本可读的状态、变更与验证摘要
  receipts.jsonl    # 决策、执行与证据的关联记录
  artifacts/        # 按配置保留的完整输出或恢复材料
```

工作区中的代码改动仍由正常的代码审查和版本控制流程处理。产品不会仅因为任务完成就自动提交、推送、合并或部署。

`report` 默认本地查看。用于分享的导出应主动排除凭据和不必要的任务正文、源码、工具参数；包含原始材料的记录不得默认变成公开报告。

## 10. 首次启用、费用与数据范围

安装默认关闭 Jev 增强能力。首次启用时，需要让用户明确知道使用哪个决策服务、可能发送什么内容，以及允许的请求范围和预算。

| 模式 | Jev 请求 | 是否依据 Jev 改变执行 | 适用场景 |
| --- | --- | --- | --- |
| off | 不发起新请求 | 否 | 原生使用、故障回退、无 Jev 对照 |
| shadow | 在已允许的数据范围和预算内发送 | 不改变工具、续跑和上下文 | 观察建议是否合理、评估开销 |
| on | 仅对已启用能力按需发送 | 在已有授权和对应验证边界内改变 | 有限启用经过验证的能力 |

**shadow 仍然可能增加网络等待和费用，也仍然会发送允许范围内的数据。它不能被称为零开销模式，不能代替无 Jev 的性能对照。**

路由通常只需要任务意图和候选描述；动作评审可能需要相关代码和证据；上下文评分可能涉及历史内容。产品应按能力说明这些范围，并尽量减少发送的数据。本地能读取文件不自动代表允许把它发送到其他服务。

用户授权过的当前任务不要求重复确认每个普通步骤。新高影响动作、超出预算或扩大数据发送范围则不能自动放行。产品不改写 provider 或模型设置；它们由用户在 Pi 或 magpie 中管理。

关闭功能会阻止新的增强动作，并使旧判断失效；已经完成的文件修改和外部行为不会因此自动撤销。需要回退时，产品应展示实际状态，而不是宣称“关闭即恢复原状”。

## 11. 首版做到哪里

**首个可交付版本必须包含真实的单执行者开发闭环：启动任务、选择工具、读取、编辑、新建文件、执行授权检查、明确完成或阻塞，并交付运行记录。**

“宿主负责执行”是一条实现边界，不应成为产品只能输出建议、不能完成实际开发工作的理由。

| 交付范围 | 内容与条件 |
| --- | --- |
| 首版必备 | Pi 扩展、薄 CLI、工具选择、真实单任务执行、完成检查、结果报告、清楚的关闭与回退行为 |
| 通过对应验证后启用 | 有界续跑、选择性强制评审；每项分别显示真实状态 |
| 实验性可选能力 | 请求级可恢复裁剪；必须先通过内容保全、恢复和净收益验证，不作为其他能力交付的前置条件 |
| 后续独立交付 | OMP 适配、parallel／DAG 多执行者调度、持久摘要替换；不能从 Pi 单执行者验证推导这些能力也已经可用 |
| 首版不包含 | Web 管理后台、新的通用 agent runtime、任意模型代理、自动额度爬取、全局 provider 接管、模型路由（由 magpie 负责），以及未经授权的提交／发布／部署 |

首版支持多文件任务，但不承诺跨文件修改具有数据库事务式的原子性。中途失败时如实保留和报告已发生的修改，不盲目覆盖用户或其他执行者的新改动。

## 12. 如何判断这个产品交付合格

### 12.1 使用与行为验收

产品验收从实际入口出发，不以“源码存在”或“类型检查通过”代替使用结果。

| 验收项 | 合格标准 |
| --- | --- |
| 可安装、可关闭 | 扩展只加载一次；doctor 能报告真实状态；关闭后不发起新 Jev 请求且不再应用旧决定 |
| 真实任务完成 | 从 Pi 和 CLI 入口完成定向读取、已有文件修改、新建文件及检查任务，结果能在工作区和报告中核对 |
| 尊重用户控制 | 用户选定的模型不被改写；追加约束、取消和修改任务目标均实际生效；不越过现有授权 |
| 完成状态可信 | 已完成、未完成、阻塞、取消及验收不可用都能正确呈现；不能将评估异常显示为验收通过 |
| 续跑有界 | 只推进具体未完成动作；次数和预算上限生效；用户新输入和外部阻塞不会被自动忽略 |
| 裁剪可恢复 | 完整输出先成功保存，再裁剪；读取可恢复原内容；失败时保留原文，图片和必要历史不丢失 |
| 报告可解释 | 改动、检查、失败和用量对应本次任务；缺失数据明确标记，失败尝试不从报告里消失 |

### 12.2 “更快”的验证

比较单位是完整开发任务，从提交到验证结束，包含 Jev 等待、模型请求、工具执行、额外验证、续跑、缓存失效和恢复读取。不能只比较某一次模型响应，或只看成功任务而删掉失败样本。

第一阶段目标沿用整合方案：任务耗时中位数降低至少 20%，p95 不恶化超过 10%，并且任务质量无实质回退、每个完成任务的总费用不高于可比较基线。**这些是试验目标，不是已经实现的产品卖点。**

原生对照与增强组应使用相同任务、仓库起点和同一个固定模型；工具选择、完成控制、上下文裁剪先分别比较。模型路由由 magpie 负责，不设本产品的试验臂；试验不使用会轮换成员的 magpie 路由组，避免把“换了模型”混进工具裁剪等收益。

质量和费用证据不足时继续观察，不宣称性能目标已经达成。某项优化没有净收益，可以默认关闭，不影响其他已验证能力继续交付。

## 14. 产品交付定义

项目实施完成时，用户应该能够在一个真实项目里提交开发任务，并得到三样东西：**实际完成的工作、能解释完成状态的验证依据，以及可以继续追查的运行记录。**

首次版本的产品边界是“Pi 中可用的开发任务增强工具”。router 为任务选择合适的工具，模型路由交给 magpie，harness 让工作持续推进到可核对的结果，可恢复 context 在证明有收益后降低长任务负担。

交付演示应同时覆盖一个修复任务、一个包含新文件的功能任务，以及检查失败、Jev 不可用和用户取消；结果可从工作树与本地报告核对，回放不会再次执行操作。

第 1 至 14 节是产品定义。首版代码已实现，逐项实施与验证状态见第 15 节；提效试验尚未运行，不据此宣称性能提升。实现与验证要求见 [技术方案](pi-jev-harness-technical.md)。

### 15.3 当前可用命令

以下命令均在仓库根目录执行。`pi-jev` 尚未发布，开发期用 `node src/cli.ts` 调用同一入口。

```text
pnpm typecheck
pnpm test
pnpm test:host
pnpm bench:offline
pi --extension <仓库目录>/src/adapters/pi/index.ts
node src/cli.ts --version
node src/cli.ts run [--cwd <目录>] [--json] [--max-time <90s|10m|1h>] [--] <任务...>
node src/cli.ts doctor [--json]
node src/cli.ts report <run-id|路径> [--json]
node src/cli.ts report <run-id|路径> [--export <file.json>] [--export-md <file.md>] [--force]
node src/cli.ts report --telemetry [目录] [--json]
node src/cli.ts replay <run-id|路径|receipts.jsonl> [--trusted <file.json>] [--json]
```

- **`pnpm test`**：运行 `tests/unit` 下的单元测试，不访问网络。
- **`pnpm test:host`**：用真实 Pi 和本地假 Jev 运行两个宿主测试，会发出真实模型请求。默认模型可用 `PI_JEV_HOST_PROVIDER`、`PI_JEV_HOST_MODEL` 覆盖。原用于模型路由 shadow 测试的候选列表变量随模型路由移除。
- **`pnpm bench:offline`**：运行 bench 自身的测试，再用本地脚本化服务跑一次离线冒烟，不发真实模型请求。
- **退出码**：0 表示命令成功且任务为 completed；1 表示命令无法完成、产物缺失或任务 failed；2 表示任务为其他非 completed 状态（含 native_off）；3 表示 replay 发现不一致；运行中第二次 SIGINT/SIGTERM 退出 130。
- **环境变量**：`TYPESAFE_API_KEY` 是唯一的 Jev 密钥来源；`PI_JEV_URL` 覆盖 Jev 地址；`PI_JEV_RUNS_DIR`（绝对路径）覆盖运行目录；`PI_JEV_RUN_ID` 指定运行编号。

### 15.5 `/jev status` 的实际输出

状态为多行文本，依次包含以下各行；方括号内是可能出现的取值。

```text
Jev: [off|shadow|on] (this session)
config: [<路径> | defaults (no file at <路径>) | invalid (<原因>); forced off; file left unchanged: <路径>]
outbound: [task intent allowed (credential check on) | 任务意图出站未开启 (outbound.taskIntent=false; no Jev request is sent)]
on: 只有已配置且已通过门槛的能力改变行为；其余按 shadow 观察          （仅 on）
工具路由：[关闭 | 仅观察 | 开启（尚无任务） | 已应用（N 个工具，M 个前置；常驻：…；任务结束已恢复） | 已回退（原因） | 外部改动已保留]
模型路由：由 magpie 负责（harness 不处理）
上下文裁剪（请求级）：[关闭 | 仅观察（本任务候选 N，可省约 M 字符；备注） | 已应用（N 条已存档） | 已回退（原因）]
摘要替换：关闭（原生路径）
Jev key: [present|missing]
Jev requests this session: N
fallback reasons: [none | 原因; …]
harness: [off (no envelopes, reviews or run products) | <mode> (envelopes checked and recorded; …) | <mode>; enforced kinds: … | <mode>; enforced kinds observed only: …]
harness actions this session: N (validation failed N, blocked N[, would block in on N], reviews sent N)
harness run products: [none yet (next: <目录>) | <目录> (written|write failed|task in progress)]
harness last error: <原因>                                             （仅出错时）
强制评审：[关闭 | 无 | create,overwrite | 仅观察（shadow 不拦截：…）]
完成验收：[关闭 | 开启 | 不可用（原因，不发请求）]
续跑：[关闭 | 启用 | 仅观察（shadow 模式不续跑） | 仅观察（harness.continuation.enabled=false）]，已用 N/M

```

配置含旧 `router.models` 键时，config 行附一条“已忽略”的提示。`/jev mode on` 的回复会附“实际生效：…”，列出上面的工具路由、上下文、强制评审、完成验收和续跑各行。在 `pi -p` 打印模式下，`/jev` 命令没有可见输出。
